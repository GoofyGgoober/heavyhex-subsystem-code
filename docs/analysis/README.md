# Paper analyses

These post-run analyses read the saved experimental records in `runs/`. They use no QPU
time and do not change `src/` or `runs/`. The table below maps the paper's results to
their scripts and distinguishes the current comparisons from additional diagnostics.

Run from the repository root with the pinned environment (see the main README):

```bash
python docs/analysis/run_all.py      # every light step, then the ledger: a few minutes
python docs/analysis/ledger.py       # only the ledger: results/paper_numbers.json and .txt
```

Each script writes `results/<script>[_<variant>].json`, which is committed. A script whose
name has a suffix (`decoder_faults.py`) is a heavy step that feeds the summary script of its
prefix (`decoder.py`). Large intermediates go to `cache/` (git-ignored) and are rebuilt on
demand. Heavy steps run with `--workers 2` by default; more workers need more memory, about
0.5 to 2 GB each. `ledger.py` computes nothing: it collects historical paper numbers,
with their sources, into `results/paper_numbers.json`. The table below also maps later
checks that are not in that ledger.


The primary stored-prediction comparison is regenerated separately with
`OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python docs/analysis/stored_priors.py`.
It holds the f=1 decoder fixed on device and model. The `primary` field name in
`stored_priors.json` is retained for the matched rate summary; the manuscript's lead
fixed-depth comparison is regenerated by `python docs/analysis/early_depths.py`. The older `f_treatments.json`
keeps the original adaptive-device comparison and the exploratory input treatments;
those rows are not all matched-decoder validation. No command here changes `runs/`.

persistence, and Fig. F1 combines the Kingston probabilities and exponential residuals.
Table F1 gives Kingston input variants. Additional diagnostics remain available but are
not substitutes for the paper's matched-decoder comparisons.

```bash
python docs/power.py runs/ibm_fez-2026-10-0{4,5,6,7,8}-r{1,2-d3,2-d5} --out docs/analysis/results/power.json
```

The defaults are seed 1 and 2,000 simulated experiments per rate. This is a retrospective
sensitivity calculation, not a power guarantee for the current fixed-depth analysis.

Shared modules, not run: `common.py` (paths, the jobs, readout series), `fitting.py` (the
weighted-log and binomial fits), `matching.py` (the decoder's graph), `leakage.py` (the
leakage fit's jobs, statistics and cached simulations), `frame_sim.py`, `exact_sim.py` and
`tableau_ref.py` (the three leakage simulators), `detectors.py` (detector classes, edge types,
the p_ij estimator and learned priors) and `refit.py` (fits of re-decoded shots, paired
bootstrap).

## IBM's properties snapshot

`calibration.json` keeps each qubit's readout error, the mean of P(1|0) and P(0|1), but not the
two separately, nor IBM's initialization error. `properties.json` adds them. It was fetched
after the run with each day's calibration time as the query time, and IBM serves the latest
snapshot strictly older than the time asked, so each day's entry is the snapshot before the
one the jobs ran under (`served`, 36 to 84 minutes earlier). Its readout errors are the ones in
force on all 156 qubits on days 1–3, and on one qubit on each of days 4 and 5 (relay q51 has
4.7% in it on day 4, against 48.6% in force). So the analyses read it only through
`properties.py`, which keeps a qubit's P(1|0), P(0|1) and initialization error only where its
recorded readout error is the one in force, taking the initialization error to come with the
readout calibration: every qubit on days 1–3, one on each of days 4 and 5. Elsewhere resets
and readouts keep the readout error in force, as in the model. Run as a script,
`properties.py` now fetches the snapshot in force and checks it against `calibration.json`;
that needs an IBM account, so the committed file is the earlier one.

Rerun with these inputs: `readout_ibm.py`, `readout.py`, `calibration_inputs.py` and
`hmm_causes.py`; every exact rerun (`leakage_rerun.py --jobs`, days 4 and 5 only, since days
1–3 have the inputs they had); `leakage_grid_bootstrap.py` and `leakage_lifetime.py`; and the
grids near their optima only, to keep the load down (the other points are dropped):
`leakage_grid_identity.json` holds the 14 best points of the earlier 53-point grid (loss up to
0.23), the best point's two other neighbours, and seeds 22–24 at the four best;
`leakage_grid_pi.json` the 3 best of 23; `leakage_grid_dephase.json` both points; and
`leakage_grid_dephase_frame.json` the 6 best of 100. Not rerun, so still with the earlier
snapshot on days 4 and 5: the frame simulator's files (`leakage_frame_*`),
`leakage_recovery.py`, `leakage_roundcond.py`, `leakage_heldout.py`, and parts C, D and X of
`leakage_checks.py`, which compare simulators on the same inputs.

## The left-out CZ in frame_sim.py

A leaked qubit's CZ is meant not to act. `frame_sim.py` propagates Pauli frames against a
reference sample of the full circuit, so with a leaked operand it applies the CZ with that
operand's noiseless Z value instead of leaving it out. The two differ only when that value
is a definite 1. No CZ operand in the fit jobs' 1- and 8-round memory circuits has a definite
Z value (0 of 24,960; `leakage_checks.py`, part E). An exact simulation of the left-out CZ (`exact_sim.py`,
checked against `tableau_ref.py`) gives the frame simulator's grid losses and Table rerun back
within Monte Carlo noise (`leakage_fit.json`). Every result of the frame simulator used
`skipped_cz="reference"`, its default, except the `leakage_frame_*` files named after another
mode.

## Reproducibility

Counts and rates decoded from the chip's shots repeat exactly anywhere, and quantities fitted
to them to within floating-point rounding. The binomial fits stop at an optimizer tolerance,
so they repeat to about 1e-7. Anything from seeded sampling (stim, and `tableau_ref.py`, which
draws from stim) repeats exactly only on the same platform and stim build, and otherwise
within its noise. The committed results come from two machines, Windows x86-64 (CPython
3.14.3) and Linux; the header of `requirements-lock.txt` lists the packages in which the
Windows environment differs from the pinned one.
